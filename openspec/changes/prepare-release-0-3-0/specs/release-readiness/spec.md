## Problem Statement

The tree carries a version it has never released and a changelog section for
a tag that was never pushed. `openspec_graph/__init__.py` reads `0.2.0`;
`CHANGELOG.md`'s `[0.2.0]` preamble says publication happens when the tag is
pushed; `docs/distribution-plan.md` records, from `origin` and from PyPI, that
no `v0.2.0` tag exists, that `release.yml` has never run and that
`pip install planlint` 404s. Everything since — three rules, the line hits,
the stage-citation report, the per-directory agent files, the `tools/`
floors, milestone M0's workflow hardening and its 0.4.0 notice for Python
3.10 — sits under `[Unreleased]`. The release that carries it is 0.3.0, and
the plan's M1 exit criterion is that the tag is published and
`pip install planlint==0.3.0` runs `validate` on this repository.

A release here is a set, not a literal. The version is hand-written in three
frontmatter fields of the distributable skill and bound to the package by
tests that already exist; two plugin manifests are generated from it; the
changelog needs a section and a link definition a test checks for; and the
adopter-facing files that a grep for copyable tag tokens finds — six files,
eight tokens at `ea40bc2`; the command is in the Evidence — name `v0.2.0` as
the tag to switch to. The `specgraph` alias has been deprecated since the
rename with no removal version anywhere a user reads. The publish step's
PEP 740 attestations are a default of the PyPA action that this tree states
nowhere, that holds only for action versions at or above the release that
made it the default, and that the sibling `pin-actions-by-sha` fixes to one
commit which Dependabot will move. This spec makes the tree release-ready,
states the deprecation windows, declares the attestation behaviour, guards
the bump set so the 0.4.0 bump is one literal and one regeneration with the
suite naming the rest, and writes the maintainer's steps down. It is the last
of the three M1 packages to land, because it moves the whole `[Unreleased]`
body of the changelog and every sibling's entry must be under that heading
first. Pushing the tag and publishing are outside the tree; what the
maintainer observes afterwards is recorded in `tasks.md`.

## Decisions

- **DEC-REL-001** (amended after adversarial review, MEDIUM-5)**:** the
  release is 0.3.0 and `v0.2.0` is never tagged. The version `0.2.0`
  existed in the tree from 2026-09-12 — the day PR #25 folded the earlier
  `2026-09-02` heading and everything after it into one section — and was
  installable from git by commit, so its changelog section is a record of a
  real version and stands — heading, date, body and link — with one
  appended sentence. That sentence says three things because three things
  in the section are now misleading: the date is the fold day, not a tag
  day (the section's own "the date is the first public tag, not the freeze"
  was written as a promise and is now false, and is left as the record of
  what was promised); the tag was never pushed; and the
  `[0.2.0]: …/releases/tag/v0.2.0` link definition is kept because
  `test_every_changelog_version_links_to_its_release_tag` requires one per
  versioned heading and its docstring already accepts a link to a tag that
  does not resolve — so a reader is told it will not. Rejected: tagging
  `v0.2.0` retroactively on its commit, which would trigger `release.yml`
  and publish a nine-month-old tree to an immutable index; folding `[0.2.0]`
  into `[0.3.0]`, which rewrites a dated record and contradicts the
  "release-train honesty" entry that refused to split 0.2.0 in the first
  place; retargeting the `[0.2.0]` link at a commit, which the test forbids
  by shape; and deleting the "not the freeze" sentence, which is history.
  The honest statement goes in both preambles: 0.3.0's says it is the first
  tag and first publication; 0.2.0's says what its date is and that its tag
  never came.
- **DEC-REL-002** (amended after adversarial review, MEDIUM-5)**:** the cut
  follows Keep a Changelog 1.1.0 in this file's own spelling. The heading
  is `## [0.3.0] — <date>` with the em dash every released heading here
  uses, not the specification's hyphen, because the test reads the
  bracketed version and a mixed file is a diff nobody asked for. The date
  is written as the day the tag is intended to be pushed — the convention
  the `[0.2.0]` entry announced and could not keep — and the release commit
  and the tag are made in one sitting; if the sitting slips, the date is
  amended in the commit that gets tagged, so the date on the tagged commit
  is the tag's day. Nothing in the tree can verify a date against a tag
  that does not exist yet, so R-REL-4 requires the intent and the amendment
  rule, and `tasks.md` records the tag's commit and date after the fact.
  The body moves verbatim: the entries were written as they landed, and
  rewriting them at release time is where a changelog starts describing
  what someone remembers rather than what shipped. An empty
  `## [Unreleased]` stays at the top because the specification keeps one
  there always and every contributor's next entry needs a place to go; it
  gets the `compare/v0.3.0...HEAD` link the specification shows, which the
  file has never had because there was no tag to compare from.
- **DEC-REL-003:** no new test pins the SKILL.md fields. The plan's W1.5
  text makes the test conditional — "if none does today" — and the
  condition is false: `test_skill_metadata_version_matches_the_package`
  holds `metadata.version`, `test_ci_template_pins_the_floor_the_skill_enforces`
  holds `planlint-min-version` equal to `__version__`, and
  `test_compatibility_prose_matches_the_declared_minimum` holds the
  `compatibility:` number equal to `planlint-min-version`. Three lines,
  three bindings, in two modules that already exist. A fourth test would be
  a second copy of a check, which is the drift shape this repository keeps
  refusing. The two prose mentions on lines 178–179 are the gap, and the
  `@v…` one falls under the guard of DEC-REL-004; the bare one is edited by
  hand in the same change and listed in the checklist.
- **DEC-REL-004** (amended after adversarial review, LOW-7, LOW-8)**:** the
  bump-set guard is a test in `tests/test_adopter_urls.py`, not a script
  under `tools/`. That module already discovers the adopter corpus
  (`_adopter_files()`, globbed, with `openspec/` excluded and a presence
  floor on the corpus), already imports `__version__`, and already houses
  the test that polices the own-action ref; a `tools/` check would have to
  re-implement that corpus stdlib-only and then be wired into a `make`
  target, a workflow and the runnable-script parametrize list for the same
  assertion. Scope is copyable instructions — tag tokens an adopter would
  paste — never bare mentions: the module's own docstring explains that
  merged change packages and dated records are history, and
  `docs/peer-review-2026-10.md` saying "`v0.2.0` is still untagged" is a
  true sentence about October that must stay true. The pattern is anchored:
  `(?<![\w/.-])@v\d+\.\d+\.\d+|ianshank/planlint\S*@v\d+\.\d+\.\d+|rev:\s*v\d+\.\d+\.\d+`.
  The first alternative is a `@v<semver>` not glued to a path — the prose
  form in SKILL.md, README and the distribution plan; the second is this
  project's own action ref in its `uses:` form, which *is* glued to a path
  and must still be caught; the third is the pre-commit `rev:`. A
  third-party `owner/repo@v7.0.1` matches none of them, so the guard cannot
  mistake another project's tag for this one's. The anchoring is belt and
  braces: `pin-actions-by-sha` leaves every third-party ref as
  `@<sha> # vX.Y.Z`, whose comment carries no `@`, and before it lands they
  are bare majors (`@v7`), so no third-party `@v<semver>` is expected in the
  corpus in either state — but a guard that is correct only because of a
  sibling's posture is a guard with an unstated precondition. `CHANGELOG.md`
  is excluded by name because the root `*.md` glob catches it and its
  `[0.2.0]` body legitimately says `@v0.2.0` 404s; the review re-ran the
  grep and found the by-name exclusion sufficient. The test asserts the
  match set is non-empty first, for the reason the module gives twice: a
  scan over zero matches is a pass that proves nothing. The set it polices
  is not counted in any requirement: it is whatever the grep in the
  Evidence prints at the commit it is run on (eight tokens in six files at
  `ea40bc2`), and `tasks.md` records the red run's offender list at the
  branch head rather than a number. With this guard the 0.4.0 bump is one
  literal, `make skill-manifests`, and `make test` naming every remaining
  hand edit — the SKILL.md fields, the changelog section and link, and
  every tag ref — which is as close to one command as a hand-written
  surface gets without a generator this change declines to add.
- **DEC-REL-005** (amended after adversarial review, MEDIUM-3)**:** the
  `specgraph` window is stated where each audience reads: in the warning
  itself for the person running `specgraph`, in the `[0.3.0]` `Deprecated`
  group for the person reading release notes, in the README alias paragraph
  for the person choosing a command, and in the `[project.scripts]` comment
  for the person editing the entry points. The general rule the window is
  an instance of — announced under `Deprecated` in the notes of a minor
  release 0.Y.0 naming the removal version, working and warning through
  the whole 0.Y.x series, removable from 0.(Y+1).0 (its R-POL-3) — is
  `write-down-policies`' and lives in `docs/policies.md`; this package
  does not restate it. The `Deprecated` line itself is written once,
  by whichever package is in the tree first: `write-down-policies` writes it
  under `[Unreleased]` and the verbatim move of R-REL-4 carries it into
  `[0.3.0]`; if this package lands into a tree without it, this package
  writes it. Two packages on one branch writing one CHANGELOG line is a
  duplicate or a merge conflict, which is why R-REL-6 says "contain", not
  "add", and why the landing order of DEC-REL-011 puts this package last.
  The warning is the one every alias user sees, so it names the version; the
  new sentence keeps the existing first sentence intact because
  `test_deprecated_alias_keeps_stdout_parseable` asserts its substring, and
  a new test asserts `0.4.0` appears. The removal is 0.4.0 and not now
  because 0.3.0 is the first release anyone installs from an index: a
  user migrating CI from a git install meets the alias and its notice at
  the same time, and a full minor version is the notice the 3.10 removal

- **DEC-REL-006** (amended after adversarial review, HIGH-1, MEDIUM-2)**:**
  attestations are declared, verified by the maintainer, and not re-verified
  by a job. The plan says the behaviour needs no change, and the behaviour
  does not change: `attestations: true` is the action's default, and has
  been since v1.11.0 — the input arrived in v1.10.0 with `default: false`
  and marked experimental, and v1.11.0 flipped the default; the sibling's
  pin, v1.14.2, carries it non-experimental and on. It is declared anyway
  because a default is a property of a version, and the version is now a
  pin that Dependabot moves and a human can re-pin: `pin-actions-by-sha`
  lands first and fixes the publisher at
  `@dc37677b2e1c63e2034f94d8a5b11f265b73ba33 # v1.14.2`, so the comment
  tells a reader which version runs, but nothing in the workflow says that
  the release depends on that version being at or above v1.11.0, or what
  happens if it is not. An explicit input survives the pin and states the
  dependency: at or above v1.11.0 it is a no-op; against a v1.10.x pin it
  is what turns attestations on, so the line strengthens rather than merely
  documents; older than v1.10.0 the action does not know the input and
  GitHub raises an "Unexpected input" warning annotation on the run — a
  visible signal where the default would have gone quietly missing. The
  comment on the step says exactly this (R-REL-10), so a future pin is read

  and not the ref, because the ref is the sibling's: a test here that
  pinned `release/v1` would go red the moment the sibling landed, and one

  for three reasons: the index is not guaranteed to serve the new files the
  instant the upload returns, so a job would need retries to observe a
  state it just wrote; the verifier pulls a signing stack into whatever
  environment runs it, and `[project] dependencies = []` and the unpinned
  dev extras are both load-bearing decisions this package does not reopen
  for a once-per-release observation; and a job that asserts PyPI's state
  from inside the workflow that produced it proves less than a maintainer's
  shell reading the index from outside. The step is two commands: the
  Integrity API
  (`GET https://pypi.org/integrity/planlint/0.3.0/<filename>/provenance`,
  no install, HTTP 200 with at least one bundle whose publisher is GitHub)
  proves presence, and `pipx run pypi-attestations verify pypi
  --repository https://github.com/ianshank/planlint pypi:<filename>` proves
  the bundle verifies against this repository's identity. Both results are
  recorded in `tasks.md`. Rejected: adding `pypi-attestations` to the dev
  extra (every contributor pays for a release-day tool); a post-publish job
  (above); and relying on the PyPI web page's "Provenance" badge alone
