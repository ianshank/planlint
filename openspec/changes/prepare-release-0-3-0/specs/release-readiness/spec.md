# Spec: Release Readiness

> **Change:** `prepare-release-0-3-0`
> **Version:** 1.0.0-draft
> **Authors:** maintainer · reviewer
> **Status:** DRAFT

---

## Problem Statement

The tree carries a version it has never released and a changelog section for
a tag that was never pushed. `openspec_graph/__init__.py` reads `0.2.0`;
`CHANGELOG.md`'s `[0.2.0]` preamble says publication happens when the tag is
pushed; `docs/distribution-plan.md` records, from `origin` and from PyPI, that
no `v0.2.0` tag exists, that `release.yml` has never run and that
`pip install planlint` 404s. Everything since — three rules, the line hits,
the stage-citation report, the per-directory agent files, the `tools/`
floors, milestone M0's workflow hardening and its 0.4.0 notice for Python
3.10 — sits under `[Unreleased]`. The release that carries it is 0.3.0, and
the plan's M1 exit criterion is that the tag is published and
`pip install planlint==0.3.0` runs `validate` on this repository.

A release here is a set, not a literal. The version is hand-written in three
frontmatter fields of the distributable skill and bound to the package by
tests that already exist; two plugin manifests are generated from it; the
changelog needs a section and a link definition a test checks for; and seven
adopter-facing files name `v0.2.0` as the tag to switch to. The `specgraph`
alias has been deprecated since the rename with no removal version anywhere
a user reads. The publish step's PEP 740 attestations are a default of the
PyPA action that this tree states nowhere, and the next package pins that
action to a SHA. This spec makes the tree release-ready, states the
deprecation windows, declares the attestation behaviour, guards the bump set
so the 0.4.0 bump is one literal and one regeneration with the suite naming
the rest, and writes the maintainer's steps down. Pushing the tag and
publishing are outside the tree; what the maintainer observes afterwards is
recorded in `tasks.md`.

**Evidence:** measured at drafting, this tree. `__version__ = "0.2.0"` at
`openspec_graph/__init__.py:15`, read by `pyproject.toml` through
`dynamic = ["version"]`. `skills/planlint-spec-governance/SKILL.md` carries
`0.2.0` on lines 5, 7 and 8 and `v0.2.0`/`@v0.2.0` on lines 178–179;
`tests/test_agent_skill_docs.py::test_skill_metadata_version_matches_the_package`,
`::test_compatibility_prose_matches_the_declared_minimum` and
`tests/test_adopter_urls.py::test_ci_template_pins_the_floor_the_skill_enforces`
bind the three frontmatter lines to `__version__`; nothing binds the prose.
`.claude-plugin/plugin.json` and `marketplace.json` are generated by
`tools/render_plugin_manifests.py` from `__version__`, and both `--check`
generators exit 0. `CHANGELOG.md` line 6 is `## [Unreleased]` and line 408 is
`## [0.2.0] — 2026-09-12`; `### Deprecated` at line 45 carries the 0.4.0
removal of 3.10; the only link definitions are `[0.2.0]` and `[0.1.0]`;
`test_every_changelog_version_links_to_its_release_tag` requires a heading
and a tag link for `__version__`. `.github/workflows/release.yml`: `v*` tag
trigger plus `workflow_dispatch`; `gate` runs `make pre-pr`; `build` builds,
checks wheel metadata, smoke-tests the console script in a venv and fails
when the tag and `planlint --version` disagree; `publish` runs under
`environment: pypi` with `id-token: write` and
`pypa/gh-action-pypi-publish@release/v1` with no `with:`. The action's
`action.yml` on `release/v1` declares `attestations` with `default: 'true'`,
"Only works with PyPI and TestPyPI via Trusted Publishing". PyPI's
`GET /integrity/<project>/<version>/<filename>/provenance` returned HTTP 200
with one GitHub-published bundle for `pypi-attestations` 0.0.30 when probed.
`openspec_graph/cli.py:1010–1013` `_DEPRECATION_WARNING` ends "and will be
removed." with no version; `tests/test_cli_surface.py` asserts the substring
"is deprecated; use `planlint`" on stderr and the exit code preserved.
Copyable tag refs (`@v<semver>`, `rev: v<semver>`) outside `CHANGELOG.md` and
`openspec/`: `templates/spec-gate.yml:63`, the asset copy's line 63,
`SKILL.md:179`, `README.md:417`, `.pre-commit-hooks.yaml:11`,
`docs/distribution-plan.md:15,132,138` — all `v0.2.0`. Every other `0.2.0`
under `tests/` is a fixture or a comment, and the golden hashes normalise
`tool_version`. `make stage-citations`: `pre-pr` is run by `release.yml`,
`e2e-live` and `docs-check` by `ci.yml`, `wheel-check` by no workflow and
already on another package's verification line.

## Requirements

- R-REL-1: `openspec_graph/__init__.py` MUST read `__version__ = "0.3.0"`,
  and it MUST remain the only version literal in code: `pyproject.toml`
  keeps `dynamic = ["version"]` and the `attr:` source, and no module, test
  or tool restates the number as a literal compared against a release.
- R-REL-2: The three frontmatter fields of
  `skills/planlint-spec-governance/SKILL.md` — the numeric version in
  `compatibility:`, `metadata.version` and `metadata.planlint-min-version` —
  MUST equal `__version__`, held by the tests that already bind them. No new
  SKILL.md field test is added. The two prose mentions of the tag in the
  "Wiring it into CI" section MUST name `v0.3.0`.
- R-REL-3: `.claude-plugin/plugin.json` and `.claude-plugin/marketplace.json`
  MUST be regenerated by `make skill-manifests` and MUST be fresh under the
  generator's `--check` mode at the release commit. Neither file is edited
  by hand.
- R-REL-4: `CHANGELOG.md` MUST gain a `## [0.3.0] — <date>` heading, in the
  file's existing em-dash form, whose date is the day the tag is pushed.
  Every line that sat under `## [Unreleased]` at the release commit MUST
  move under it verbatim, keeping its `###` groupings and order, including
  M0's `Changed` entry and the `Deprecated` notice for Python 3.10. An empty
  `## [Unreleased]` heading MUST remain at the top. The link definitions
  MUST gain `[Unreleased]: https://github.com/ianshank/planlint/compare/v0.3.0...HEAD`
  and `[0.3.0]: https://github.com/ianshank/planlint/releases/tag/v0.3.0`.
- R-REL-5: The `[0.3.0]` section MUST open with a preamble stating that
  `v0.3.0` is the first tag pushed under the `planlint` name and the first
  release published to PyPI, and that `v0.2.0` was never tagged. The
  `[0.2.0]` section's heading, date, body and link definition MUST stand;
  its preamble gains exactly one sentence saying the tag was never pushed
  and pointing at 0.3.0. No other released section changes.
- R-REL-6: The `Deprecated` group under `[0.3.0]` MUST state the `specgraph`
  window — the alias warns through 0.3.x and is removed in 0.4.0 — beside
  the retained Python 3.10 notice. The same window MUST appear in
  `README.md`'s alias paragraph and in the `[project.scripts]` comment of
  `pyproject.toml`.
- R-REL-7: `_DEPRECATION_WARNING` in `openspec_graph/cli.py` MUST name the
  removal version `0.4.0` and the window `0.3.x`, MUST keep the substring
  "is deprecated; use `planlint`" the existing tests assert, and
  `main_deprecated` MUST keep writing it to stderr only and returning
  `main`'s exit code unchanged. The `specgraph` entry point in
  `pyproject.toml` MUST NOT be removed.
- R-REL-8: Every copyable tag reference in the adopter corpus
  `tests/test_adopter_urls.py` discovers — a `@v<semver>` token or a
  `rev: v<semver>` token in any file of `ADOPTER_FILES` other than

- R-REL-13: `README.md`'s "Not on PyPI yet" note and Action-section prose,

- R-REL-14: The post-publish observations — the `release.yml` run id and

- C-REL-6: Pushing the tag, publishing, and every PyPI or GitHub setting
  are the maintainer's actions outside the tree. Nothing in this package
  performs them, and no criterion below claims a pass for one that has not
  been observed and recorded.

## Decisions

- **DEC-REL-001:** the release is 0.3.0 and `v0.2.0` is never tagged. The
  version `0.2.0` existed in the tree from 2026-09-12 and was installable
  from git by commit, so its changelog section is a record of a real
  version and stands — heading, date, body and link — with one appended
  sentence saying the tag was never pushed. Rejected: tagging `v0.2.0`
  retroactively on its commit, which would trigger `release.yml` and
  publish a nine-month-old tree to an immutable index; folding `[0.2.0]`
  into `[0.3.0]`, which rewrites a dated record and contradicts the
  "release-train honesty" entry that refused to split 0.2.0 in the first
  place; and retargeting the `[0.2.0]` link at a commit, which
  `test_every_changelog_version_links_to_its_release_tag` forbids by shape
  and whose docstring already accepts that a version link may point at a
  tag that does not resolve. The honest statement goes in both preambles:
  0.3.0's says it is the first tag and first publication; 0.2.0's says its
  tag never came.
- **DEC-REL-002:** the cut follows Keep a Changelog 1.1.0 in this file's own
  spelling. The heading is `## [0.3.0] — <date>` with the em dash every
  released heading here uses, not the specification's hyphen, because the
  test reads the bracketed version and a mixed file is a diff nobody asked
  for. The date is the day the tag is pushed — the `[0.2.0]` entry already
  states "the date is the first public tag, not the freeze" — so the release
  commit and the tag are made in one sitting, and if the sitting slips the
  date is amended in the commit that gets tagged. The body moves verbatim:
  the entries were written as they landed, and rewriting them at release
  time is where a changelog starts describing what someone remembers rather
  than what shipped. An empty `## [Unreleased]` stays at the top because the
  specification keeps one there always and every contributor's next entry
  needs a place to go; it gets the `compare/v0.3.0...HEAD` link the
  specification shows, which the file has never had because there was no
  tag to compare from.
- **DEC-REL-003:** no new test pins the SKILL.md fields. The plan's W1.5
  text makes the test conditional — "if none does today" — and the
  condition is false: `test_skill_metadata_version_matches_the_package`
  holds `metadata.version`, `test_ci_template_pins_the_floor_the_skill_enforces`
  holds `planlint-min-version` equal to `__version__`, and
  `test_compatibility_prose_matches_the_declared_minimum` holds the
  `compatibility:` number equal to `planlint-min-version`. Three lines,
  three bindings, in two modules that already exist. A fourth test would be
  a second copy of a check, which is the drift shape this repository keeps
  refusing. The two prose mentions on lines 178–179 are the gap, and the
  `@v…` one falls under the guard of DEC-REL-004; the bare one is edited by
  hand in the same change and listed in the checklist.
- **DEC-REL-004:** the bump-set guard is a test in
  `tests/test_adopter_urls.py`, not a script under `tools/`. That module
  already discovers the adopter corpus (`_adopter_files()`, globbed, with
  `openspec/` excluded and a presence floor on the corpus), already imports
  `__version__`, and already houses the test that polices the own-action ref;
  a `tools/` check would have to re-implement that corpus stdlib-only and
  then be wired into a `make` target, a workflow and the runnable-script
  parametrize list for the same assertion. Scope is copyable instructions
  — `@v<semver>` and `rev: v<semver>` tokens — never bare mentions: the
  module's own docstring explains that merged change packages and dated
  records are history, and `docs/peer-review-2026-10.md` saying "`v0.2.0`
  is still untagged" is a true sentence about October that must stay true.
  `CHANGELOG.md` is excluded by name because the root `*.md` glob catches
  it and its `[0.2.0]` body legitimately says `@v0.2.0` 404s. The test
  asserts the match set is non-empty first, for the reason the module gives
  twice: a scan over zero matches is a pass that proves nothing. With this
  guard the 0.4.0 bump is one literal, `make skill-manifests`, and
  `make test` naming every remaining hand edit — the SKILL.md fields, the
  changelog section and link, and every tag ref — which is as close to one
  command as a hand-written surface gets without a generator this change
  declines to add.
- **DEC-REL-005:** the `specgraph` window is stated where each audience
  reads: in the warning itself for the person running `specgraph`, in the
  `[0.3.0]` `Deprecated` group for the person reading release notes, in the
  README alias paragraph for the person choosing a command, and in the
  `[project.scripts]` comment for the person editing the entry points. The
  warning is the one every alias user sees, so it names the version; the
  new sentence keeps the existing first sentence intact because
  `test_deprecated_alias_keeps_stdout_parseable` asserts its substring, and
  a new test asserts `0.4.0` appears. The removal is 0.4.0 and not now
  because 0.3.0 is the first release anyone installs from an index: a
  user migrating CI from a git install meets the alias and its notice at
  the same time, and a full minor version is the notice the 3.10 removal
  already gives. The window "through 0.3.x" is written as such rather than
  as a date because releases here are tag-driven and undated in advance.
- **DEC-REL-006:** attestations are declared, verified by the maintainer,
  and not re-verified by a job. The plan says the behaviour needs no change,
  and the behaviour does not change: `attestations: true` is the action's
  default, fetched from its `action.yml` at drafting. It is declared anyway
  because W1.2 will replace `release/v1` with a 40-hex SHA that carries no
  version a reader can check against the release that introduced the
  default, and a behaviour relied on by default and stated nowhere is the
  "config that looks like a gate and is not" shape `pyproject.toml`'s own
  comments call out. An explicit input survives the pin: a guard asserts it,
  the comment names the floor the pin must satisfy, and a pin too old to
  know the input produces a visible "unexpected input" annotation where the
  default would have gone quietly missing. Verification after publish is a
  maintainer step, not a post-publish job, for three reasons: the index is
  not guaranteed to serve the new files the instant the upload returns, so
  a job would need retries to observe a state it just wrote; the verifier
  pulls a signing stack into whatever environment runs it, and
  `[project] dependencies = []` and the unpinned dev extras are both
  load-bearing decisions this package does not reopen for a once-per-release
  observation; and a job that asserts PyPI's state from inside the workflow
  that produced it proves less than a maintainer's shell reading the index
  from outside. The step is two commands: the Integrity API
  (`GET https://pypi.org/integrity/planlint/0.3.0/<filename>/provenance`,
  no install, HTTP 200 with at least one bundle whose publisher is GitHub)
  proves presence, and `pipx run pypi-attestations verify pypi
  --repository https://github.com/ianshank/planlint pypi:<filename>` proves
  the bundle verifies against this repository's identity. Both results are
  recorded in `tasks.md`. Rejected: adding `pypi-attestations` to the dev
  extra (every contributor pays for a release-day tool); a post-publish job
  (above); and relying on the PyPI web page's "Provenance" badge alone
  (presence without verification).
- **DEC-REL-007:** the own-action ref flips from the SHA to `@v0.3.0` only
  after the tag exists, as one post-tag commit, and the interim SHA is not
  advanced. `test_ci_template_pins_the_floor_the_skill_enforces` holds both
  states — a 40-hex SHA with `@v{__version__}` named in the file before the
  tag, `v{__version__}` after — so the flip is a one-line edit per file the
  suite accepts in either order, never a window in which an adopter is
  handed a 404. The SHA is not moved to the release commit beforehand
  because the action installs the CLI from its own checkout: the only
  reason to advance it would be to hand adopters 0.3.0 code before the tag,
  and the tag arrives in the same sitting. `harden-ci-workflows` C-HCW-3
  and DEC-HCW-012 already name `docs/distribution-plan.md` as the owner of
  this switch, which is why the runbook step lives there. The README's
  "Not on PyPI yet" note is deleted in the same commit, as it says to be.
- **DEC-REL-008:** the runbook goes in `docs/distribution-plan.md` §3 and
  the recurring checklist in `docs/hooks.md`; no new document. §3 is already
  this runbook for 0.2.0, step by step, with the publisher registration,
  the dry run, the tag, the watch and the flip; rewriting it for 0.3.0 keeps
  one place the README already links. The checklist is what every future
  bump needs and belongs in the durable contributor document
  `tools/check_docs.py` requires and `make docs-check` gates, in the section
  that already states the policy that a skill change ships in a package
  release. The plan's W8 finding on documentation sprawl argues against a
  third file, and its W9.3 release skill will read these two.
- **DEC-REL-009:** criteria that can only be observed after the tag — the
  workflow's three jobs green, the attestations on the published files, the
  fresh-venv install running `validate` — cite the local stage that is
  their equivalent (`make pre-pr`, which `release.yml`'s `gate` runs by
  name, or `make e2e-live`, which runs the installed console script against
  this repository as `ci.yml` does) and name the observation in the
  criterion, with the result recorded in `tasks.md` under the run id. This
  is `harden-ci-workflows` DEC-HCW-013's pattern. Neither stage is new to
  the set no workflow invokes by name, so the citation adds nothing there.
  A criterion stays unchecked until the observation is recorded; the gate
  passes on an unchecked box, and a checked box without a recorded
  observation is the claim this repository refuses to make.
- **DEC-REL-010:** the guard's exclusions are named, not implied. Fixtures
  under `tests/` that spell `0.2.0` — a METADATA fixture the wheel checker
  never compares, `tool_version` values handed to the SARIF renderer,
  frontmatter strings fed to the parser — are not the package version and
  do not bump; the golden hashes already normalise `tool_version` so a bump
  re-pins nothing. Historical prose — "Changed in 0.2.0", "Since 0.2.0 the
  distribution…", the dated review tables — stays. Listing them here is so
  the implementer does not "fix" them and so the adversary can check that
  the guard's scope matches this list.
